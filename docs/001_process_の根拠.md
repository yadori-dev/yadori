# 進め方の根拠

この文書は、[進め方](000_process.md)を疑ったときにだけ読む。規則の写しではなく、なぜ今の形にしたかを残す。

## 結論

yadori は、別のプロジェクトで運用して結論の出た進め方をそのまま採る。増分ごとにV字を保ち、先に体験と受入基準を選び、要件とシステムテスト、設計と結合テストを対にしてから実装し、下から順に確かめる。同じ判断を複数の文書へ写さず、期待する体験はIssue、増分のV字は一枚のINC、実装後の観測はPRへ集約する。

**この形が良いという根拠は、yadori 自身の観測ではない。** 別のプロジェクトでの運用で得られたものであり、この製品でも同じ効果が出るかは未確認である。合わない箇所が観測されたら、その観測を根拠に変える。

## なぜV字を保つか

実装から考え始めると、テストは「書いたコードが動くか」の確認へ寄りやすい。先に次の順で決める。

1. その人は、どんな場面で何に困っているか
2. 何ができるようになれば受け入れられるか
3. 外から見て、どんな振る舞いなら要求を満たすか
4. どの境界と責任分担で実現するか
5. どの実装がその設計を動かすか

確認は逆向きに進む。結合テストで設計を、システムテストで要件を、最後に実際の利用で受入基準と体験を確かめる。

これは工程を一度で固定するためではない。上の約束に穴が見つかったら、実装で埋めず、その段へ戻るための構造である。

## なぜ同じ判断を写さないか

一つの増分について、要件、設計、テスト項目、増分記録、アイデア台帳、現在の構造へ同じ判断を書くと、直すたびに別の写しが壊れる。レビューの中心が「要求を満たすか」ではなく「写しが揃っているか」へ移り、検査を重ねても収束しない。

そこで、増分で同時に変わる `SPEC`、`ST`、`AD`、`IT`、`IDEA`、節目を同じINCへ置く。別の一覧が必要なら、本文を写さず機械で導出する。

## この製品で特に効くと考えている点

以下は推定であり、まだ観測していない。

- **思い出す質は文章の受入基準で判定できない。** 先に受入基準を決める工程を持っていると、判定できないことに実装前に気づける。実際、この製品では判定手段そのものをADRで決める必要が生じた（[ADR-010](010_decisions/ADR-010-思い出す質を評価セットで判定する.md)）
- **後戻りが高い判断が、立ち上げ時点で複数ある。** 記憶の保存の形、持ち主の扱い、原文とインデックスの関係は、後から変えると利用者の記憶そのものを失う。ADRを先に置く工程がないと、これらは実装の途中で暗黙に決まる
- **この製品は年単位で育てる。** 何をなぜ決めたかが残らないと、二年後に自分の判断を再現できない

## 見直す条件

工程そのものが増分の進行を妨げていると観測されたとき。妨げの内容を Discussion の振り返りへ残し、この文書を先に直してから工程を変える。
