# 開発プロセス

## 何を守るための進め方か

一つの増分で、利用者の困りごとから実装後の確認までをつなぐ。

```text
背景・課題 → 要求・受入基準 → 要件・システムテスト → 設計・結合テスト
                                                        ↓
確認結果   ← PR            ← 実装・実行できるテスト    ←
```

左側で「何を満たすか」と「どう確かめるか」を先に決める。実装後は右側から順に、設計、要件、受入基準を満たしたか確かめる。これを増分ごとに繰り返す。

大事なのはこの対応であって、文書の数や長さではない。同じ説明を工程ごとに写さない。

## 1. 文書の役割

- Issue は、誰がどの場面で困り、体験をどう変えたいかを持つ
- `docs/110_requirements/` は、増分をまたいで生きる背景、課題、シナリオ、要求、受入基準を持つ
- `docs/210_increments/INC-nnn.md` は、一つの増分の要件と設計、それぞれに対応するテスト設計を持つ
- コードと実行できるテストは、決めた要件と設計を実現する
- PR は、実際に操作して観測した結果と、Issue から変わった点を持つ
- `README.md` と `docs/150_system/` は、現在の使い方と現在の構造を持つ
- ADR は、後から戻す費用が高い判断と、その理由を持つ
- Discussion は、決まる前の質疑、まだIssueにするほど固まっていないアイデア、増分ごとの振り返りを持つ
- Git と Issue・PR の会話は、変更とレビューの履歴を持つ

別の文書に同じ説明が要る場合は、正典へリンクする。検討した全案、レビューの指摘一覧、工程を守った証拠は、現在の仕様へ転記しない。

## 2. 識別子が表すもの

識別子は、文章を短くするためではなく、上下の対応を検索できるようにするために使う。

| 識別子 | 表すもの | 対応先 |
|---|---|---|
| `PB` | 観測した困りごと | `REQ` |
| `SC` | 困りごとが起きる一連の場面 | `AC` |
| `REQ` | 手段を決めずに表した要求 | `AC` |
| `AC` | 要求を満たしたと判定できる状態 | Issue と `INC` |
| `IDEA` | 実現手段の候補 | 選んだ `SPEC` または `AD` |
| `INC` | 一つの体験を完成させる増分 | Issue と PR |
| `SPEC` | その増分で満たす外から見える振る舞い | `ST` |
| `ST` | `SPEC` を外の入口から確かめるシステムテスト | 実行できるテストまたは手動確認 |
| `AD` | `SPEC` を実現する構造と責務の判断 | `IT` |
| `IT` | `AD` の境界と採用理由を確かめる結合テスト | 実行できるテスト |

番号はリポジトリ全体で重複させない。廃止した番号を別の意味で使い直さない。番号だけを書かず、必ず意味が分かる短い名前を添える。

## 3. 要求分析

要求分析は、増分をまたいで生きる事実を扱う。増分の途中では変えず、増分を閉じた区切りでだけ見直す。

1. `PB` に、誰がどの状況で何に困ったかを書く
2. `SC` に、その困りごとが起きる場面を最初から最後まで書く
3. 要求の漏れや判定方法に確立した理論があるか、作った本人と別の学者役が一次情報で確かめる
4. `REQ` に、手段を含めず、できる必要があることを書く。理論を使った場合は一次情報と限界を指す
5. `AC` に、第三者が満たしたか判定できる状態を書く。理論からこの場面へ当てはめた箇所は推論と明記する
6. 確認できていない人物、数字、因果は未決事項へ残す

本人の発言、観測した事実、そこからの推定を混ぜない。顧客名や個人名など、公開してはいけない情報は抽象化する。

## 4. Issue で体験を決める

一つの Issue で、関係する人の体験を一つ変える。次を、設計文書を読まなくても分かるように書く。

- 誰が、どんな状況で、何に困っているか
- 変更前にできないことと、変更後にできること
- 誰が、どの入口で、何をし、何が見え、次に何を判断できるか
- CLI、GUI、API、定期処理など、変更する入口の実際の入力と期待する結果
- 関係する `PB`、`SC`、`REQ`、`AC`
- 完了と判断できる状態と、今回扱わないこと

関係しない入口を形式的に並べない。要求から見てありそうな入口を作らない場合だけ、見落としではなく対象外だと一行で示す。

Issue が百五十行を超えたら、複数の体験を混ぜていないかを見直す。別文書へ説明を移して見かけだけ短くしてはならない。

## 5. 増分の計画

Issue を実装できる大きさにすると決めたら、`docs/210_increments/INC-nnn.md` を一枚作る。この一枚を、増分の左側の正典にする。

冒頭には、対応する Issue と選んだ `AC` を書く。作業中、確認中、完了などの状態は Issue と PR が持つ。増分文書へ写さない。

作業は次の節目を順に通す。

1. 体験を検討中
2. 要件とシステムテストを検討中
3. 設計と結合テストを検討中
4. 実装中
5. 確認中
6. 結果の確認

節目を進める前に、前の段が独立した検査を通ったことを確かめる。指摘一覧は増分文書へ写さず、Issue または PR の会話へ残す。

## 6. 候補を出す

満たし方に有力な候補が複数あるときは、決める前に候補を出す。最初から一案に寄せず、独立に出した案を突き合わせる。

増分をまたいで残す候補は、Discussion の「アイデア」カテゴリへ一件ずつ置く。誰がどの場面で困り、何を変えたいかが固まり、実装すると決めたらIssueにする。候補を一冊の台帳へ写さない。

候補を比較した会話はDiscussionに残し、増分文書には判断に残った候補だけを `IDEA` として一行ずつ書く。選んだ理由と落とした理由は、判断を再現できる短さにする。単なる思いつきや、実装中に自然に決まる細部へ番号を振らない。

## 7. 要件とシステムテストを対にする

選んだ `AC` から、その増分で必要な振る舞いを `SPEC` として導く。同時に、各 `SPEC` を外から確かめる `ST` を設計する。

`SPEC` には、入力、結果、状態変化、失敗時の返り方、意味のある境界を書く。内部の層、保存方法、クラス名は書かない。

`ST` は一件ずつ、対応する `SPEC`、実際に使う入口と入力、観測する結果を書く。異なる判断だけに番号を付け、同じ規則の値違いは一つの表駆動テスト（入力と期待結果を表で並べて同じ手順を通すテスト）へまとめる。

一つの `SPEC` に対応する `ST` が無ければ、満たしたと判定できない。`ST` から上位の `SPEC` を指せなければ、そのテストは作る理由が無い。

ここで独立した検査役が、Issue、選んだ `AC`、`SPEC`、`ST` を突き合わせる。通るまで設計へ進まない。

## 8. 設計と結合テストを対にする

各 `SPEC` をどの責務と境界で実現するかを `AD` に書く。同時に、その境界と採用理由を確かめる `IT` を設計する。

`AD` に残すのは、複数箇所を一緒に変える構造、責務の置き場、依存の向き、失敗時にどこが何を返すかである。ファイル一覧や処理の逐語説明は書かない。

後から戻す費用が高い判断は、増分文書だけで終わらせず ADR にする。公開 API、保存形式、データ移行、外部との契約が代表例である。ADR には判断、必要になった状況、選択肢、理由、不利益、見直す条件だけを書く。

`IT` は一件ずつ対応する `AD`、入力、観測する結果を書く。単にコードが動くことではなく、その構造を選んだ理由を確かめる。境界を越えて同じ規則が働くこと、依存先を差し替えられること、責務が外へ漏れていないことなどを見る。

ここで別の独立した検査役が、`SPEC`、`AD`、`IT` と現在の構造を突き合わせる。通るまで実装へ進まない。

## 9. 実装する

実装は `SPEC` と `AD` をコードにし、先に設計した `ST` と `IT` を実行できるテストにする。

- 利用者の体験に近いテストから作る
- テスト名に対応する `ST` または `IT` を含める
- テスト対象を意図的に壊し、対応するテストが落ちることを確かめる
- 外から見える API を変えたら、正典と生成物を同じ変更で直す
- 現在の使い方や構造を変えたら、`README.md` または `docs/150_system/` を同じ変更で直す
- 手元の確認には使い捨ての保存先を使う

実装中に要件の不足が見つかったら、黙ってコードへ足さず、`SPEC` と `ST` へ戻る。構造の不足なら `AD` と `IT` へ戻る。戻った段から下だけを再検査する。

## 10. 下から満たしたか確かめる

実装後は次の順で確認する。

1. `IT` が通り、`AD` の境界と採用理由が実現している
2. `ST` が通り、`SPEC` の振る舞いが外の入口から成立している
3. Issue の中心となる流れを実際に操作し、選んだ `AC` を満たしている
4. 対象となる人ごとに、期待した体験の変化が起きている

テストが通っただけで、実際の利用の流れを確認済みとしない。確認できない環境や人の評価は、未確認と書く。

## 11. PR に結果を書く

PR は実装後の結果である。Issue や増分文書を写さず、次を書く。

- 実際にできるようになったこと
- 中心となる流れを実際に通した入力と観測結果
- 実行した `ST`、`IT`、その他の検査と結果
- Issue や増分計画から変わった点と理由
- 確認していないこと、満たせなかったこと、今回の対象外

要求が変わった場合は Issue を、要件や設計が変わった場合は増分文書を先に現在の計画へ直す。PR は `Closes #<Issue番号>` で Issue を閉じる。

実装を作った本人とは別の検査役が、Issue、増分文書、コード、テスト、現在の文書、PR の結果を突き合わせる。解決しない指摘は PR の会話に残し、別の作業なら Issue に分ける。

## 12. 増分を閉じる

選んだ `AC` を満たし、未確認と対象外が明記され、独立した検査を通ったら、PR に結果を書いてマージする。PR のリンクだけを増分文書へ足す。

マージ後は、Discussion の「振り返り」カテゴリへ `INC-nnn 振り返り: <体験の名前>` を一件作る。詳しい結果はPRを指し、次の三つを書く。

1. 前回の振り返りで、この増分が終わるまでにやると決めたことを一件ずつ確かめる。できたことは結果を書く。未実施なら、やらないと決めた理由、または必要なのにできなかった理由と次の扱いを書く
2. この増分で見つけたことと感じたことを書く。実装だけでなく、工程、準備、意思決定、作業量、気持ちも対象にする
3. 次の増分が終わるまでにやることを決める。すべての所感を宿題にせず、約束するものだけを選ぶ

具体的な作業にするものはIssueへ移す。所感やレビュー回数を一冊の台帳へ積み上げない。

次の増分を始める前に、直前の振り返りを読む。次でも効く判断が出た場合だけ、この工程、要求、現在の設計へ反映する。リポジトリに振り返りの台帳は持たない。

### 完了後に不足を見つけた場合

まず、元の要求を一度も満たしていなかったのか、満たした後の変更で壊れたのか、新しい期待が増えたのかを分ける。

- 元の要求を一度も満たしていなかった場合は、元の Issue と同じ増分を開き直し、不足した段まで戻る。同じ約束に新しい増分や識別子を重ねない
- 満たした後の変更で壊れた場合は、不具合の Issue と修正用の増分を作る。元の要求と設計を指し、再び壊れない確認を加える
- 新しい期待が増えた場合は、新機能の Issue と増分を作る。元の増分へ後付けしない

増分文書は、現在の要件、設計、必要なテストだけへ直す。見つけた日、再開した理由、レビューの往復は Issue、PR、Git に残し、現在の設計へ混ぜない。

開き直した増分は、不足と関係する `IT`、`ST`、中心となる操作を下から順に確かめ、独立した検査を通してから再びPRへ結果を書く。識別子を埋めるためのテストは増やさず、同じ判断の値違いは既存のテストへまとめる。

## 13. 文書の書き方

用語に詳しくない読者が、一度で意味を取れる文章にする。

- 結論を先に書き、その理由を後に置く
- 実際の対象がディレクトリ、プロセス、権限なら、その言葉を使う
- 技術用語が最も正確なら使い、初出で何をするものかを一文で説明する
- 一文に一つの判断を書く。注釈と履歴を本文へ重ねない
- 入力と結果、比較、対応関係は表やコード例にする
- 現在の説明に、過去の検討順やレビュー履歴を混ぜない
- 未確定なことを推測で埋めない

Issue または一つの増分文書が百五十行を大きく超えたら、体験を分けるか、同じ内容を重ねていないかを見直す。`just stats` で文書とコードの分量を確認する。

## 14. 機密情報

顧客名、参画先名、本人以外の個人名、非公開リポジトリの URL、社内のホスト名、契約条件、絶対パス、端末名を書かない。Issue、PR、Discussion、コミットメッセージも同じである。

非公開資料から構造や様式を学んでよいが、その内容、出典、所在は書かない。認証情報は `gitleaks`、固有の禁止語は `scripts/check-confidential.sh` で検査する。

## 15. Git と自動検査

ブランチ、コミット、PR、環境構築、コーディング規約は [`CONTRIBUTING.md`](../CONTRIBUTING.md) に従う。

`just check` は、機密、依存の向き、生成物、テスト、識別子の重複と上下の対応を確認する。増分文書に書いた個々の `ST` と `IT` は、作業状態にかかわらず、実行できるテストまたは手動確認へ必ずつなぐ。機械は文章の妥当性や利用体験を承認できないため、独立した検査を省略しない。
